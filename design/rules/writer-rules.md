# 项目写作规则

本文档是一套「反 AI 味」的写作方法论：五步教学节奏 + 语气/句式规范，写非虚构教程类书籍时通用。开始写新书时，先把下面例句里的占位内容换成自己书的领域，方法论本身不用大改。

---

## 教学节奏：五步弧线

每章遵循融合 Productive Failure、5E 模型和认知学徒制的五步节奏：

1. **建立动机（Engage）**：用具体问题或具体场景开场，让读者先知道这一章在解什么实际问题。不写「本章学习 X」，写「这一章解决：在 Y 情况下需要 Z」。情绪刺激（「让读者先渴」「让读者感同身受」）不是这一步的目的，问题清楚才是。
2. **带着问题尝试（Explore）**：读者知道自己在试图解决什么问题。步骤有引导但不是纯机械执行，留出空间让读者形成自己的疑问。
3. **讲解原理和设计哲学（Explain）**：做完后解释底层发生了什么、为什么要这样设计、不这样做会怎样。带着实践经验回头听原理，听得进去。
4. **变式练习（Elaborate）**：让读者自己改着玩。不给完整答案，给方向。「把颜色换成绿色试试？」「故意删掉这个组件看看会发生什么？」触发生成效应和自我解释。
5. **回顾与连接（Evaluate）**：三句话总结：刚做了什么、现在能做什么、下一步去哪。

关键原则：第 ① 步不能跳过。略过问题直接给步骤，读者只是在抄操作，不是在学习。

### 钩子的设计

第 1 步「建立动机」常用具体场景或具体问题切入。具体场景天然排他。对不上的读者会从"被讲到"翻成"被假设"。三种写法按优先级排：

1. **首选：客观事实钩子**。把动机锚定在所有翻书读者都共有的事实上（如"想做出 X""这件事要解决三个问题"）。工程类教程的默认开局。避免「你」做主语。
   - ✓「【领域】里有一些【产出】，做出来的效果是这样的。许多人见过之后，开始想自己做一个。」
   - ✓「一个最基础的【产出】要回答三件事：从哪开始、中间要经过什么、怎么知道做完了。」

2. **次选：邀请框 + 精确画面**。确实需要读者代入特定场景时，外层加一句邀请框承认场景的非普遍性，内层全是具体动作和感官。
   - ✓「也许你也有过这样的瞬间。某天深夜，手挡住光带时有体积光泛起……」

3. **反模式：纯精确无邀请的"你"开头**。「你在【某场景】里瞎逛」做主语会假设读者经历过这件事，对不上的人立刻退出。

**最大公约数原则**：钩子的命中率 = 锚定事实在目标读者中的覆盖率。"你曾在某时某地有过某情绪"命中率有限；"想做 X"「需要 Y」命中率接近 100%。能锚现在就不锚过去，能锚意图就不锚经历。

**呼应回路要保留**：开头抛出的具体形象（场景细节、某句疑问、某个画面），后段引用时不要替换成空泛代词。
- ✗ 前文「写给那个凌晨两三点的你」 → 后文「写给你的」（具体抓手丢了）
- ✓ 前后文保留同一个具体形象，形成回路

**判断标准**：合上前言走的读者里，有没有人是因为"觉得这书不是写给我的"而离开。如果有，钩子排他了。

## 理解章（概念章）

在动手章之间穿插短的「理解章」或「视角章」：

- 不要求动手操作，专门帮读者建立更完整的心智模型
- 回答「为什么是这样」——设计哲学、底层原理、历史原因
- 把前面做过的具体操作提升为可迁移的通用概念
- 篇幅不超过动手章的一半，保持轻快

理解章的位置：每一部的末尾或开头，作为「呼吸」。让读者从具体操作中抬起头来，看一看全景。

## 创作者视角

在每一部的开头或末尾加一节「创作者视角」短文（500–800 字）：

- 把技术操作连接回创作意图
- 回答「这跟我想做的那件事有什么关系」
- 如果这本书的主题也是"创造"一类东西，可以在这里传达那种意义感：你在做一个别人能用上、能走进去、能感受到的东西

## 侧栏系统

正文中穿插四类侧栏（旁白框），统一使用 Astro Starlight 的内置 Markdown 容器语法（`:::容器类型[标题]`），严禁在正文中通过手写 Emoji 和粗体拼凑来充当侧栏标题。这能确保在各种尺寸的屏幕（包括手机端）上都能渲染出精美、统一个性化背景与图标的提示框：

- **🤔「为什么是这样？」** — 统一写为 `:::tip[为什么是这样？]`。展示专家思维，讲设计决策的原因。对应认知学徒制的 Modeling。每个「为什么」都应该包含「如果不这样会怎样」的对比。
- **⚠️「坑」** — 统一写为 `:::caution[踩坑预警]`。记录真实踩过的错误，具体到哪个按钮、哪行代码。对应 Coaching。
- **🤖「AI 能帮忙」** — 统一写为 `:::note[AI 小助手]`。当前情境下怎么问 AI，怎么验证 AI 的回答。
- **🔀「不同世界不同活法」** — 统一写为 `:::note[不同世界不同活法]`。同一技术在不同世界类型里的不同用法，促进远迁移。

## 难度渐进（专家反转效应）

- 前几章（第一部、第二部）：步骤极细，每一步都写清楚点哪里、填什么值
- 中段（第三部、第四部）：步骤逐步简化，开始省略已经讲过的基础操作
- 后段：只给方向和关键节点，鼓励读者自己查文档和探索
- 每次省略步骤时，确保读者在前面已经做过至少两次相同操作

## 句式

- **禁用波折号（——）**。中文写作里常用来制造延展感或补充感的破折号，是 AI 文风的高频信号。一律改为冒号、逗号、句号，或拆成两句话。规则文档里如果非要展示这个字符本身（如本条），仅作字符引用，不当连接词使用。
  - ✗「具体场景天然排他——对不上的读者会从被看见翻成被假设。」
  - ✓「具体场景天然排他。对不上的读者会从被看见翻成被假设。」
  - ✗「【某产出】可以是 A，也可以更多——它能同时是 B、C、D。」
  - ✓「【某产出】可以是 A，也不止于 A：它同时是 B、C、D。」
- **避免过碎的短句和频繁的无意义换行**：中文行文应当保持高度的连贯性与阅读呼吸感。严禁将一句话拆成好几个两三个字的极短单句并独立成段，防止在网页端渲染时产生过多琐碎留白、无端拉长滚动条，从而降低信息承载效率。
- 先说要什么，再说不要什么。读者先拿到答案，再处理可能的误解
  - ✗「不是最完美版本。不是最完整版本。是最小版本。」（先堵了两次再给答案）
  - ✓「要的是最小版本：能跑、能理解、测试通过。」（直接给答案）
  - ✓「要的是最小版本。完美和完整是以后的事。」（答案在前，补充在后）
- 避免「不是 A 而是 B」「不…而…」「不要以为 X，其实是 Y」这类绕行句式。直接说 B / 直接说 Y
- 如果确实需要消除误解，把否定放在肯定后面作为补充，别当开头

## 结构

- 正文不写 h1 标题。页面 h1 由 frontmatter 的 `title` 自动渲染（Starlight 行为），正文从 h2（`##`）开始
- **章节标题用动作或承诺，不用「的目的/介绍/概述」**。标题是契约：读完这一节，能拿走什么 / 能做到什么 / 能理解什么。教科书式标题（"的目的""概述""简介"）等于不写。
  - ✗「这本书的目的」「关于本章」「X 简介」
  - ✓「这本书做一件事」「先把最小成果跑起来」「X 是什么样的工具」
- 每个章节聚焦一个核心概念或一个可达成的成果
- 截图和 GIF 紧跟操作步骤，减少来回翻找（空间邻近原则）
- 开头用痛点或好奇心导入，参考性内容（目录结构、部署方式等）放附录
- 技术步骤优先引用官方文档，并在章节末尾列出参考链接
- 信息融入叙事和操作流程中，避免一段话接一个表格的技术文档写法
- **表格的使用场合**：表格不是少用，而是看场合用。下面两类情况，用表格比写段落更清楚；其他情况优先正文叙述。
  - **适合用表格**：
    - 术语对照表（中英文 + 备注）
    - 快捷键 / 键位 / 命令对照
    - 几种方案的横向对比（A 方案 vs B 方案，按几个维度对照）
    - 精确数值清单（Transform 坐标、参数取值、版本号）
    - 字段说明表（组件字段名 → 作用，且字段较多时）
  - **不适合用表格**：
    - 概念解释（用段落叙述，让读者顺着读，不要让他左右扫表）
    - 单个组件的介绍（把它放进流程里讲，不要做成「字段一览」）
    - 教学步骤（步骤靠序号和段落组织，不靠表格）
  - 判断标准：信息本身是「对照 / 清单 / 横向比较」结构，用表格；信息是「线性叙述 / 因果推进」，用段落。
- 每章读起来像一份认真写过、有节奏感的工程教程。不是 API 参考手册，也不是聊天记录。
- 一次只引入一个新概念，做完、理解了，再进入下一个（认知负荷管理）

## 配图策略

- 正文先保证纯文字可跟做，配图作为增强项，不让教程依赖图片才能完成
- 不直接搬运或热链网上图片、截图和 GIF，除非来源明确允许再使用
- 可以引用官方页面链接，让读者跳转查看官方截图和界面
- 需要配图的位置先用「建议截图」备注记录，等实际操作时再补自己的截图
- 能用文字表格、路径、对象层级和参数表说明的内容，优先用 Markdown 表达
- 文字描述 + 结构图/层级树 = 利用双编码提升理解

## 语气

整本书的默认语气是**客观的工程教程**，对标的不是聊天记录、不是导师独白、不是朋友坐你旁边带你做，而是 Unreal、Unity、MDN、Vulkan Tutorial 这一类朴实、克制、节奏稳定的官方教程。

具体规则：

- **以客观陈述为默认**：操作步骤优先用动词起句，省略人称主语（「打开 Inspector」「右键创建空物体」），不写「你打开」「我们打开」。
- **「你」收紧到三种用途**：
  1. 真正需要点名读者本人状态时（「检查上一章装好的工具版本」）。
  2. 给开放式的变式练习派任务时（「自己改一下数值看看」）。
  3. 阐明产出归属时（「最后会拿到一个能上传的世界」）。
  其他场合都试着去掉「你」，看意思有没有损失。多数时候没有。
- **「我」严格限制在三种场合**，其余一律不用：
  1. 前言、关于页等真实作者自述。
  2. 作为讲述者表达倾向 / 立场（「这里建议先跑通最小版本」）。
  3. 转述外部真实案例并给出可核验来源。
  正文不写「我自己第一次……」「我那时候……」这种伪造的具身经历。
- **「我们」一律不写**。它隐含某种集体或机构口吻，距离感更远，也是 AI 文风的高频信号。
- **不写「朋友 / 带你 / 陪你 / 坐在旁边 / 指着屏幕」这类拟人化的陪伴框架**。这些表达试图制造亲近感，反而让读者一眼识别出 AI 文风或营销文案。
- **不预言读者的未来 / 内心 / 命运**。「你迟早会」「你会发现」「你心里会有数」「路是通的」这类句式都换成可观察的具体产出。
- 简洁优先，一句话能说清的别拆成两句。

## 节制：对抗 AI 默认倾向

以下规矩专门用来防治 AI 生成文本的典型病灶。每条都是硬性红线。

### 禁止假共情

- **没干过就不要用干过的口气。** 不要写「你一定会由衷地感激现在这个做了 X 的自己」「你会在 Y 时陷入疯狂」这类代替读者预言情绪的句子。
- 把「我懂你的痛苦」换成「事情就是这样」。陈述因果，不冒领经历。
  - ✗「你一定会由衷感激现在改好名字的自己」
  - ✓「名字乱起，两周后自己都分不清哪个是地板。现在花五秒改名，省的是以后的时间。」
- 成就感是读者自己做出来时产生的，不是作者替他感动出来的。禁止在读者尚未完成操作时提前替他欢呼。

### 禁止伪造作者的具身经历

本书由 AI 协作生成。前言和「关于」页已经向读者交代过这件事，正文里就不要再伪造作者第一人称的踩坑回忆。读者对 AI 文风敏感度很高，一眼能识破「我那时候 / 半小时后我才意识到 / 我老老实实去 Add Component 里搜」这类伪造经历，反而损伤信任。

- ✗「我自己第一次做这件事时，问 AI 该怎么办，它递回来一个听起来对的方案，让我『照着做就行』。我老老实实去试，试不通。半小时后我才意识到：这东西它编的。」
- ✓「AI 经常会编不存在的细节。一个常见的例子是它会让你『用某个听起来专业的方法』，但这个方法查不到出处，搜不出来很正常。」

允许的「我」用法见前面「语气」节，不在此重复。

禁止的写法：虚构具体的时间、地点、心路历程（「半小时后」「凌晨三点」「我盯着屏幕意识到」）以装出曾经亲历。

### 禁止替读者宣告内在状态

把「你会觉得 / 你心里会 / 你迟早会 / 路是通的」这类替读者打包票的句子全部换成可观察的具体产出。读者的"会不会、通不通"应当是他自己读完后自己判断的，不是作者替他宣告的。

- ✗「怎么让一个空间像一个地方，你心里会有方向。」
- ✓「怎么让一个空间像一个地方：书里会给一组可套用的检查清单。」
- ✗「发布之后怎么维护、更新、继续学，路是通的。」
- ✓「发布之后怎么维护、更新，书里也会讲。」
- ✗「卡了的时候不是只有你卡。」
- ✓「这些工具的设计有自己的历史包袱，对新手不友好是常态。」
- ✗「你迟早会向 AI 求助。」
- ✓「这一章讨论一个可选项：如果用 AI 协助做这件事，怎么用得对。」

判断方法：把句子里关于读者内心 / 命运 / 未来的预言部分删掉，看剩下的事实陈述够不够撑起这一句。够，就留事实；不够，重写。

### 禁止教练腔（爹味）

把读者放在「还没开窍的新手」的位置说话，再以过来人姿态布置任务，是 AI 文风另一种典型病灶。和上一节「替读者宣告内在状态」是姊妹问题：那一条预言读者**命运**，这一条预言读者**犯错**，并接着布置改正方案。爹味通常叠了四层：

1. **预设读者会犯错**——「新手碰到第一次报错的常见反应是 X」「新手最容易卡的是 X」「养成 X 的习惯」。把读者锚定在"还没开窍"的位置。
2. **命令式祈使**——「不要 X」「记住 X」「务必 X」「把这两点记牢」。下指令，没给推理空间。
3. **后果绑定（威吓 / 利诱）**——「能省掉大半夜调试」「省的是以后的时间」。拿后果换读者的服从。
4. **箴言式总结**——「报错越早出现，现场越干净，原因越容易找」。把朴素经验包装成训词。

改写思路：把「你应该 X」换成「X 是这样运作的」，让读者自己推出该怎么做。三条具体操作：

- **去掉读者人称归类**。不写"新手……老手……"，直接讲事情。「新手最容易踩的笔误」→「最容易踩的笔误」（删掉"新手"，事实没变）。
- **把指令改成机制描述**。「不要一口气写五十行再运行」→「Unity 在每次保存 .cs 文件时都会重新编译一次。改几行保存一次和写完一大段再保存，错误暴露的时机会差很多。」（陈述编辑器机制，让读者自己推出节奏）
- **去掉后果绑定**。「养成 != null 检查的习惯，能省掉大半夜调试」→「在调用之前加一行 != null 检查，能把这类空引用挡在事件中断之前」（后果指向上下文里讲过的具体技术现象，不指向读者的睡眠 / 时间 / 情绪）。

判断方法：把句子里所有对读者的称谓、人设归类、命令动词删掉，看剩下的事实陈述够不够撑起这一段。够，就只留事实；不够，重写。

#### 隐蔽变种：假减压

「不用全记住」「不需要背」「读完不用全部消化」这类句式表面在替读者卸压，里子是同一个权力结构：预设了读者**本来在背**，并把作者抬到了"发许可证"的位置——背不背的标准在我手里，我现在网开一面。读者本来没想背，被这句话扣了一个"想背但记不住"的人设，反而开始检查自己是不是该记。

真正不焦虑的写法是**不引入这个焦虑**——直接讲这一节的用法，不引入"该不该背"这个伪问题。

- ✗「读完不用全记住。后面章节里凡是冒出『这事在管线哪一段』的疑问，回来对一下这张图就能定位。」
- ✓「这张图后面会被反复回查。每章冒出『这事在管线哪一段』的疑问时，对一下就能定位。」
- ✗「这一章里那份白名单 / 编译器特性 / 工程化约束三类清单不需要背。」
- ✓「这一章里那份白名单 / 编译器特性 / 工程化约束三类清单是当字典用的。」
- ✗「这句话不需要背。但脑子里有这条链路的影子……」
- ✓「这句话只是一个浓缩。真正起作用的是脑子里有这条链路的影子……」

常用替代表达：「是当字典用的」「后面会反复回查」「是底图」「明白了这两点，X 就能想通」。共通操作是把"该不该背"换成"这一节怎么被用到"。

#### 豁免清单

下面三类不算爹味，不要为了"清干净"而误伤：

- **技术约束类「不要 X」**：沙箱边界、Quest 性能限制、`Update` 里堆操作这种讲客观约束的命令式，是讲规则不是判读者，留命令式反而紧凑。
- **AI 提示词模板里写给 AI 的「不要 X」**：那是提示词内容，不是写给读者。
- **真减压**：前提里就没有焦虑的句子，如「不需要先成为程序员才能开始」「Unity 不要求你写满每一个组件」——读者并没有被预设"本来在 X"，这种是真正卸压。

### 不要把可选工具描述成必经之路

很多工具（AI 助手、特定插件、特定工作流）都是可选的。把这些可选工具描述成「必经之路」是 AI 文风的另一个高频信号，也常常违背真实情况。

- ✗「做这件事绕不开 AI。」
- ✗「现代开发者都离不开 X 插件。」
- ✗「这一章的内容你迟早要面对。」
- ✓「AI 在很多情况下能帮上忙，但不是必备的。本书把它作为一种可选辅助工具来介绍。」
- ✓「X 插件能减少几步重复劳动。如果不想引入新依赖，按官方流程走也跑得通。」

例外：如果领域里确实存在事实上的标准入口（官方必装的工具、平台强制的账号体系……），可以直接陈述「做这件事以 X 为入口」，因为这是平台规则，不是建议。判断标准：是不是没有这个工具就走不下去。是平台层规则，可以陈述为事实；只是常用辅助，必须明示可选。

### 禁止诗化的空悬动作

「先把这份好奇心放在桌上看一眼」「先把它放在心里」「先站进去再慢慢看清楚」这类指令既不可执行又装深沉，是 AI 文风重灾区。

- ✗「这一章先不动手，先把这份好奇心放在桌上看一眼。」
- ✓「这一章先不动手，先把范围聊清楚。」
- ✗「先站进去，再慢慢把门后的东西看清楚。」
- ✓ 直接收尾，不写这一句。

要么直接说不做什么（「这一章不动手」），要么直接给出动作（「这一章先解释 X」）。不要让读者去执行一个无法执行的动作。

### 禁止空泛的二元对立拔高

「你做的不是 A，是 B」「X 是作品，不是地图」这种句式先把读者脑子里第一个朴素的认知（A）否定掉，再立一个更虚的 B。问题是 A 往往本身没错，读者会立刻反问「为什么不能是 A」。

- ✗「你要做的不是一张地图，是一个别人可以走进去存在的地方。」
- ✗「【某产出】是作品，不是【某类比】。」
- ✓「【某产出】比【某类比】要多承担几件事：A、B、C，有时候也是一件作品。」
- ✓「【某产出】可以是【某类比】，也不止于此：它同时可以是 A、B、C。」

改写策略：要么直接列出事物的多重身份，要么承认 A 也是其中一面。不要让读者站在被否定的那一侧。

### 禁止形容词通胀（打鸡血腔）

- 删掉所有不传递信息的形容词和副词。自检方法：把形容词/副词删掉，句子意思没变，那个词就是脂肪。
- 禁用词清单（持续补充）：「伟大的」「极其聪敏地」「栩栩如生」「由衷地」「极有成就感」「完美地」「超凡的」「光荣地征服」「极其优雅」「翻天覆地」「令人无限向往」「前所未有」「重中之重」「望而生畏」「虚无深渊」「绝对」（作强化副词时，如「绝对清晰」「绝对不会」）「史无前例」
- 技术教程里，读者要的是「我照做能不能成」，不需要被不停拍肩膀。克制。

### 禁止网络流行语和营销腔

- 禁用词清单（持续补充）：「保姆级」「大佬」「一本通」「百科全书」「YYDS」「绝绝子」「干货满满」「手把手」（作为标榜用语时）「零基础变 X」
- 这些词出现在介绍/前言/标题里，会让读者立刻识别出"这是一本割韭菜书 / AI 生成营销文案"，丧失信任。
- 想表达"全面"，就描述具体覆盖范围；想表达"详细"，就老老实实把每一步操作和参数写出来。具体步骤本身就是最强的证据，不需要贴标签。

### 禁止排比成瘾

- 三连排比（「能 A、能 B、能 C」「暖黄色……冷蓝色……」）单看漂亮，连起来读像节拍器。同一段最多出现一组三连排比，多了就拆掉或合并。
- 句式要有长短变化，节奏不均匀才是好节奏。

### 软化词的两种用法：稀释（禁）vs 邀请（留）

「也许」「可能」「大概」「或许」这类软化词不能一刀切禁，要看它在做什么工作。

**稀释画面 ✗**——把软化词注入画面内部，让具体描写本身变虚：
- ✗「也许在某天深夜」（把"深夜"也稀释了）
- ✗「也许你抄起一把剑挥了挥」（动作本身不该犹豫）
- ✗「评论区可能还有人写」（事实陈述被稀释成猜测）

**邀请代入 ✓**——在画面外层加一句框架，承认这只是一类典型场景而非普遍经历，给对不上的读者留台阶：
- ✓「也许你也有过这样的瞬间——某天深夜……」（外层邀请，画面内部仍精确）
- ✓「或者你压根没碰到过——你只是听别人说过……」（显式接住没共鸣的读者）

判断方法：把软化词删掉，看句子是变得**更准确**（说明它在稀释，该删）还是变得**更专横**（说明它在邀请，该留）。

钩子级别的软化策略见上方「钩子的设计」。

### 人称：客观陈述优先

「我」「你」「我们」三个代词都收紧。详细的用法已经写在前面的「语气」节。这里只放快速判断方法：

- 写完一段后，把里面所有「你」「我」「我们」试着删掉或改写。
  - 删掉之后意思没变（多数情况）：保持删掉的版本。
  - 删掉之后意思变了（指令对象不清、产出归属不明、作者立场需要标记）：把代词加回去，但只加不可省的那个。
- 操作步骤通篇省略主语；解释原理用客观陈述；阐明产出和邀请变式练习时才出现「你」；前言和关于页才出现「我」。
- 反复出现「你怎么样、你怎么样、你怎么样」连排的段落基本都需要重写。

### 末尾标点克制

- 末尾叹号 `！` 默认禁用。陈述句的力量来自动词和名词，不来自标点。需要语气时用句子结构表达，不用标点喊。
- 章节首尾、结语处尤其克制。读者刚要思考，被 `！` 一拍肩膀就跳出来了。

### 禁止均匀

- **允许各节长度悬殊。** 新手易错的重点写到啰嗦也行，简单的点一句话带过。禁止为了对称硬凑。
- 不是每一节都需要配一个 callout 盒子。全章 callout 控制在 2–4 个，只留给真正的坑或关键认知转折。如果发现「每节末尾必有一个 tip」，说明已经变成背景噪音了。
- 章节结尾不使用「通过本章学习你掌握了……下一章我们将……」的教科书样板。收尾可以用一句自然过渡，也可以直接接变式练习或参考链接。
- **「下一章 X」桥接句不能每章都用**。即便每句的写法都不一样，连续 N 章都以「下一章……」收尾，本身就是均匀。判断方法：通览全书目录，如果过半数章节都靠「下一章 X」过渡，就要主动挑几章删掉过渡，让它们停在变式练习、踩坑提醒或一句陈述上。

### 隐喻不重复

- 每个核心隐喻全书只展开一次。第二次出现时用一句话带过并引用首次位置，不再重新展开。
- 例：「乐高」比喻在第 5 章展开过，第 6 章不再重复，一句「还是那个乐高思路」即可。

## 促进深度学习的写法

- 做完操作后，问读者「你觉得如果改成 X 会怎样？」——触发自我解释
- 「坑」侧栏先让读者猜原因，再给答案——触发测试效应
- 不同章节间自然回顾前面的概念，不专门写「复习」章节——间隔效应
- 解释原理时用「如果不这样 → 会发生什么坏事」的对比——制造认知冲突

## 中文写作规范

本教程以正式中文教程为目标。文字应当客观、干净、统一，无翻译腔，无营销腔。

### 标点

- 正文使用中文标点：逗号 `，`、句号 `。`、冒号 `：`、分号 `；`、问号 `？`、感叹号 `！`
- 引号统一使用中文直角引号：外层 `「……」`，内层 `『……』`。不使用英文引号 `"..."` 或中文弯引号 `"…"`
- 代码、文件名、UI 控件名使用反引号：`` `Build & Test` ``、`` `Inspector` ``、`` `MyFirstWorld.unity` ``
- **「盘古之白」（中英文半角空格）**：打字时请务必在中文与英文 / 数字之间加一个半角空格（如 `Git 仓库`、`API 接口`、`Y 值是 1`）。汉学家称这个空白字符为「盘古之白」，因为它劈开了全角字和半角字之间的混沌。为了排版品质和读者的感情运势，请优雅地留出这粒空格。
- 括号里的补充说明用中文括号 `（……）`。只有纯英文内容的括号用英文括号 `(…)`：如 `PBR（Physically Based Rendering）`

### 术语处理

英文术语不硬译。保留圈内通用说法，**首次出现时用括号注明含义**，之后直接使用英文。

按自己书的领域维护一张统一术语表（持续补充），格式参考：

| 写法 | 首次出现时的说明 | 备注 |
|------|----------------|------|
| （领域术语示例） | 中文说明 | 之后直接用英文还是可混用 |

### 新手门槛词的解释方式

正文遇到新手大概率不熟悉的技术名词（如 `CDN`、`Shader`、字节码、显存、沙箱、`YAML`、`Token`），按以下三层结构处理：

1. **正文用「人话括注」一笔带过**。第一次出现时在词后用中文括号给一句不超过 25 字的口语化定义，让读者不必跳出页面就能继续读。详细解释不写在正文里。
   - ✗「沙箱是一种隔离机制，它通过限制系统调用来阻止……」
   - ✓「沙箱（给陌生代码套的「笼子」）：阻止程序访问不该访问的磁盘、网络、命令行。」
   - ✓「编译成字节码（一种比源码更紧凑、更接近机器的中间格式）」
2. **完整定义放进 `src/content/docs/appendix/glossary.mdx`**。每条 1–2 句客观定义 + 首次出现章节回链。术语表是回查入口，不是教学场。新增词条按自己书的主题归入对应分类，不要散乱堆在末尾。
3. **不要把术语表升级成独立百科页**。除非某个术语真的需要展开成几千字（届时再单开 `src/content/docs/wiki/xxx.mdx`），保持「正文一句话 + 附录回查」两层结构。过早上百科页会让导航和搜索结果变重。

哪些算门槛词（要补）：

- 第一次出现时，零基础读者会停下来想「这是什么」
- 上下文猜不出大致含义
- 不解释会直接卡住后面几段的理解
- 在书里多次出现，且后续章节会反复引用

哪些不算门槛词（不要补）：

- 通用语：凭上下文能猜的常见缩写、流行语
- 后面章节会专门展开的：某个概念会在后面某一章铺一整节，正文别抢戏，正文里写明「第 N 章会专门铺一节」即可
- 反例代码 / 反例操作里出现的具体名字：只是用来演示「这种东西不能用」，看不懂反而强化了印象，不需要解释
- 本书核心主题词：这本书的几个核心概念本身都有专章展开，不属于此规则适用范围

风格细节：

- 括注用中文括号 `（……）`，括注内部仍遵循正文风格：不用波折号、不堆排比、不写「也就是说」
- 「可以理解成 X」「可以先把它想成 X」这种「先给类比再给精确含义」的句式允许使用，前提是类比本身具体，不要又抽象又文艺
- 一段里出现的门槛词不要超过两个，否则读者括注里反复跳，正文反而读不下去；多于两个时拆段
- 一个词全书只在「首次出现」处给括注，之后直接用，不要每章都重复一次释义；后续章节的读者要看释义会自己去翻附录术语表

### 分类译名（示例）

如果书里需要频繁使用一组分类名词的中英对照，按这个格式维护一张表：

| 中文名 | 对应英文 | 说明 |
|--------|---------|------|
| （分类一） | Category One | 一句话说明 |

### 措辞

- 避免翻译腔句式：不写「在 X 中最有用的场景」，写「X 里最有用的几种情况」
- 避免英语语序的定语前置：不写「一个面向新手的领域入门教程」，写「一份给新手的领域教程」
- 「一下」「一些」「进行」等虚词能省则省
- 量词准确：不写「一个面板」（面板是平面的），写「一块面板」或直接写「面板」
- 不用「的的」「了了」等叠字
- 注意区分：
  - 「它」指事物，「他」指人，「她」指女性
  - 「做」（制作、创作）vs「作」（作为、作品）
  - 「哪里」（疑问）vs「那里」（指示）

### 数字

- 技术数值用阿拉伯数字：`0.2`、`90 度`、`3 到 10 分钟`
- 概数和日常表达用中文数字：「几万年」「十几个」「一两分钟」「二十个」

## 文档参考

**动笔前先看，不要凭印象写。** 这本书的文风、章节结构、Starlight 语法、参考资料来源都已经沉淀到下面这几份文档里。每写一章前至少扫一眼对应的那几份，避免重新发明轮子或写出和现有章节不一致的风格。

按"开始写新章"的工作流，应该这样查：

1. **`design/rules/writing-cheatsheet.md`（速查卡，每次都看）**  
   写新章的最小模板：动手章 / 理解章 / 创作者视角 / 部入口页的 frontmatter 范例、`chapterType` 与 `difficulty` 该填什么、四类侧栏（`:::tip` / `:::caution` / `:::note`）的标题写法。一页就够，**先看这个再开 mdx 文件**。

2. **`STARLIGHT-FEATURES.md`（语法参考，按需查）**  
   本站基于 Astro Starlight，所有可用的 frontmatter 字段、组件覆盖（`PageTitle` / `Footer`）、Mermaid、卡片网格、徽章、隐藏页面（`减法 frontmatter`）等等都在这里。当你想"做点速查卡里没列的东西"时翻这份。**不要在 mdx 里写未在此登记的自定义 HTML/CSS**，会和全局样式或构建打架。

3. **`design/rules/book-plan-warm.md`（全书规划，写新章前对一遍位置）**  
   全书的部 / 章规划、每章的"承诺"和大致钩子。写新章前确认：这一章在第几部？前后章是哪两章？前面已经讲过哪些概念可以直接复用（避免重复展开），后面哪一章会承接（避免抢戏）。**章节标题与 slug 也以这份为准，不要自己改**。

4. **`design/rules/pedagogy-reference.md`（教学设计理论，写不下去时查）**
   对应规则开头的「五步弧线」「专家反转」「认知负荷」等等。当你**不确定一段内容该不该写、该写多详细、该放在哪一步**时翻这份；它给的是"为什么要这样写"，不是"怎么写"。

5. **`design/rules/deploy-guide.md`（部署清单）**
   只有当你需要改部署流程或排查发布问题时才看。日常写章用不到。
